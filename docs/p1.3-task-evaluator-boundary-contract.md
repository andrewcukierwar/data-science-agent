# P1.3 + E1 task/evaluator boundary contract

This note records the independently versioned corrections made after the
2026-09-18 engineering reliability audit. The changes repair mismatches between
the public task, model-visible runtime, persisted output contracts, and offline
evaluator. They do not change the generated datasets or any expected numeric
truth or tolerance.

## Version boundaries

| Boundary | Version in new runs | Change |
| --- | --- | --- |
| Model-visible context | `2.0` | E1 allow-listed context contains the public question only. |
| Tool response contract | `1.2` | Model-facing workspace identity and embedded run identity are opaque. |
| Benchmark runner | `1.1` | New manifests freeze context, task, chart, evaluator, and audit contract versions. |
| Public scenario/task | scenario `1.1`; task contract `1.1` | Clarifies requested periods, cohort window, experiment estimand, method, and generic chart deliverable. |
| Evaluator | `1.3` | Semantic DQ type/scope matching, scoped prohibited-claim checks, and structured metric/statistic identity. |
| Audit schema | `3.0` | Separates arbitrary issue ID from issue type and structured scope. |
| Persisted run state | `1.3` | Stores classified issues with typed scope dimensions; readers retain support for earlier versions. |

The benchmark manifest remains schema version `1.0`; each newly declared run
freezes the versions above in its run configuration, including
`model_context_contract_version`, `public_task_contract_version`,
`public_chart_deliverable`, `evaluator_contract_version`, and
`audit_schema_version`. The existing run ID factory remains the immutable
internal identity source.

## Demonstrated mismatches and corrections

### E1: scenario metadata exposed through run identity

- **Old behavior:** default internal run IDs included descriptive scenario IDs.
  `inspect_workspace` returned the run ID; serialized tool results and errors
  could also contain the internal ID or absolute workspace path. This exposed
  benchmark structure and, for some scenarios, hinted at the injected cause.
- **Corrected behavior:** internal manifests, workspace names, and persistence
  continue to use the immutable descriptive run ID. Model-visible context now
  contains only the legitimate public question. Workspace inspection returns a
  stable `ws-…` identifier, and tool results/errors replace internal run IDs and
  workspace roots before serialization. Evidence lookup accepts the opaque ID
  and resolves it inside the active workspace. Relative approved file paths,
  tool events, and artifacts remain usable.
- **Version class:** E1 model-context/tool configuration; context `2.0`, tool
  contract `1.2`, benchmark runner `1.1`.
- **Why independent of model performance:** the old output directly serialized
  descriptive internal identifiers; removing them is a confidentiality and
  interface correction, not a scoring adjustment.
- **Coverage:** a sentinel scenario/cause token is checked across model context,
  workspace inspection, tool output, evidence lookup, and tool errors. Tests
  also verify persistence/resumption and evidence references still work, and
  that both architectures receive the same public task context.

### Public period and statistical task semantics

- **Old behavior:** some business tasks asked about the “latest reporting
  period” or “latest acquisition performance change,” while evaluator metrics
  were specifically Q1 2025 to Q2 2025. Experiment tasks requested a rollout
  decision and “effect size,” while the evaluator expected a particular
  treatment orientation, denominator, observation window, statistical
  procedure, and effect-size definition.
- **Corrected behavior:** current scenario `1.1` tasks name Q1 2025 and Q2 2025
  for those comparisons, state the 90-day acquired-cohort observation window,
  and define the experiment as treatment minus control over all randomly
  assigned participants with outcomes during experiment enrollment. The public
  experiment task specifies a two-sided pooled two-proportion z test, a 95%
  unpooled Wald interval, signed Cohen’s h, and assumptions. The evaluator
  consumes the corresponding structured population, dimensions, arm roles,
  window, numerator/denominator, procedure, and effect-size method.
- **Canonical task:** the canonical question already named Q2 and remains
  unchanged. Its public business definitions already establish the Q1/Q2
  comparison and 90-day definitions; no wording change was needed.
- **Data-quality scope:** the current public tasks identify the reporting window
  as 2025 Q2 or the latest available 2025 period. The exact affected day stays
  in the evaluator’s issue scope because naming it would reveal the location of
  the injected defect. That day is not a hidden comparison period: the public
  request is to audit coverage within the stated period. Regression checks
  assert that each evaluator-required date falls inside the public year/quarter
  window and that issue labels and injected causes are absent from task text.
- **Version class:** public task/scenario `1.1`; benchmark public task contract
  `1.1`. Existing v8 wording remains available as scenario `1.0`.
- **Why independent of model performance:** the task now states the same
  requested period and estimand the evaluator had already been scoring. The
  comparison values and thresholds are unchanged.
- **Coverage:** mechanical task/evaluator period checks, explicit method and
  estimand checks, canonical wording preservation, and equality assertions for
  every old/current numeric value and tolerance.

### Data-quality issue identity and evidence

- **Old behavior:** current evaluation could require an instance ID such as
  `missing_reporting_day`, although runtime issue IDs are free identifiers.
- **Corrected behavior:** `DataQualityIssue.id` remains an arbitrary instance
  identifier. `issue_type` carries semantic classification, and typed `scope`
  carries relation, date, dimensions, and value where applicable. Current
  evaluator `1.3` matches the required semantic type and exact declared scope,
  then separately requires the matching issue claim to resolve to successful
  executed evidence. A renamed ID cannot change correctness; a wrong type,
  wrong scope, or unsupported claim fails. The legacy evaluator continues to
  load and apply its original ID contract.
- **Version class:** evaluator `1.3`, audit schema `3.0`, persisted state `1.3`.
- **Why independent of model performance:** instance identifiers are not stable
  semantics, and issue claims without matching source scope or provenance do
  not establish the required finding.
- **Coverage:** arbitrary-ID metamorphic fixtures, wrong-type and wrong-scope
  failures, unsupported-provenance failure, and shifted-date/scope fixtures.

### Scoped checks for prohibited causal and null-effect claims

- **Old behavior:** phrase/token presence could reject a caution such as “this
  is an observed association, not causal proof” merely because the prohibited
  phrase appeared.
- **Corrected behavior:** evaluator `1.3` evaluates a prohibited assertion in
  its local clause and distinguishes an affirmative assertion from explicit
  negation or qualification. Double negation, “not only … proves …”, and a
  negated clause followed by an affirmative causal clause remain affirmative
  overclaims and fail. Required false literal-null assertions are handled with
  the same distinction. The check is a bounded deterministic clause rule, not a
  general-purpose natural-language parser.
- **Version class:** evaluator `1.3`; evaluator `1.2` retains the historical
  text contract for v8 evaluation.
- **Why independent of model performance:** the prior presence check did not
  represent the logical assertion expressed by the text. The correction allows
  explicit caveats while continuing to reject affirmative overclaims.
- **Coverage:** paired affirmative/negative assertions, double negation,
  adversarial “not only” wording, negation followed by an affirmative claim,
  and qualified statements about a literal null effect.

### Chart requirement versus runtime behavior

- **Old behavior:** the evaluator required a chart for evaluated completed
  cells, while runtime behavior mainly required one when the task asked for it.
- **Corrected behavior:** every current benchmark task receives the same public
  chart deliverable sentence. Runtime critic validation requires a valid,
  registered chart artifact and a candidate artifact reference. The report
  renderer includes the chart reference, and evaluator `1.3` checks that the
  final report references a valid registered chart. Both architectures use the
  same task and deterministic checks.
- **Version class:** public task contract `1.1`, benchmark runner `1.1`,
  evaluator `1.3`.
- **Why independent of model performance:** this makes the existing evaluator
  requirement explicit and enforceable at runtime; it does not remove a
  deliverable or relax completeness.
- **Coverage:** objective-visible requirement, missing/invalid/unregistered
  chart rejection, artifact-reference validation, and report-link evaluator
  checks.

### Structured metric and statistical identity

- **Old behavior:** text labels and incomplete normalization could miss
  equivalent labels for the same estimand, while the experiment evaluator
  privately expected a specific method and effect-size definition not stated
  in the task.
- **Corrected behavior:** evaluator `1.3` uses structured operation/metric,
  dimensions, baseline/comparison roles, observation window, population,
  numerator/denominator, unit semantics, treatment/control orientation,
  procedure, and bound-computation identity where applicable. Generic wording
  normalization covers equivalent labels (including arm/participant and
  proportion/fraction/rate representations when the underlying absolute rate
  estimand is the same). Display references do not define identity. A changed
  denominator, population, window, date, dimension value, segment, arm
  direction, estimand, or required procedure remains distinct. No aliases were
  added for benchmark scenario names.
- **Version class:** evaluator `1.3`; scenario/task `1.1` publishes experiment
  method and effect-size semantics. Additive optional statistical fields are
  read through the current persisted run-state contract; older workspace
  versions remain supported.
- **Why independent of model performance:** the evaluator now compares the
  declared estimand and required method instead of relying on presentation
  labels, and the formerly private experiment choices are part of the public
  task.
- **Coverage:** equivalent wording fixtures, renamed dimensions with the same
  semantic value, shifted dates, distinct denominator/window/population and
  dimensions, treatment/control reversal, required method/effect-size checks,
  and legacy evaluator behavior.

### Selected statistical records

P0.2 already made the evaluator consume the selected final statistical record
for persisted run-state schemas `1.2` and `1.3`; superseded specialist/history
records are not competing answers. P1.3 retains that behavior and adds
regression coverage. Multiple conflicting selected records still fail. No
selection redesign was made.

## Frozen v8 compatibility and numeric truth

Scenario `1.0` and evaluator `1.2` registrations preserve the old public
questions and legacy DQ ID, metric identity, chart, and text-evaluation
contracts required to load retained v8 workspaces. New task/scoring behavior is
selected by the manifest’s scenario/evaluator versions; the latest default
catalog resolution is used only for newly declared work. Persisted v8
workspaces, manifests, and results were not migrated, overwritten, or rescored
under evaluator `1.3`, and historical v8 scores must not be described as if the
new contracts had been active.

The scenario-version regression compares every ground-truth metric key,
dimension, period, expected numeric value, and tolerance between scenario `1.0`
and `1.1`, and compares experiment estimates, intervals, p-values, effect sizes,
and all associated tolerances. The test passes. The diffs do not change synthetic
data generation or numerical expected values/tolerances.

## Remaining limitations and close decision

The prohibited-claim check handles the specified local negation and adversarial
patterns deterministically; it is not a general natural-language inference
system. The exact DQ target day remains evaluator-only while the public task
states the year/quarter to audit. Docker-dependent integration tests were
skipped because Docker was unavailable. No other P1.3/E1 mismatch is known from
the requested audit scope.

**P1.3 + E1 is ready to close.** A future experiment must use newly declared
manifests that freeze these versions; frozen v8 evidence remains governed by
its original manifest and contracts.
